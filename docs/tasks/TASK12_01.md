# Queued Navigation and Abort

## Objective

Extend the existing navigation system to support queued `move_to` commands and explicit cancellation.

An agent must be able to submit multiple movement commands without waiting for each movement to finish.

## Requirements

- Preserve existing `move_to` behavior for current consumers.
- Allow `move_to` commands to be appended to a navigation queue.
- Queued commands must execute sequentially, not concurrently.
- Enqueuing must return immediately with an observable acknowledgement.
- Provide an explicit operation to abort navigation.
- Aborting must stop the active movement and clear pending commands by default.
- `navigation_status` must expose the active movement, pending queue, progress, and terminal outcomes.
- If a movement becomes blocked or fails, stop queue execution and report what happened. Do not silently skip waypoints.
- Define clear semantics for cancellation, interruption, queue limits, and invalid requests.
- Preserve existing world movement constraints and safety guarantees.

## Acceptance criteria

1. Existing single-command navigation continues working.
2. Multiple commands can be queued and execute in submission order.
3. Queue submission does not wait for movement completion.
4. Aborting during movement stops execution and prevents queued commands from running.
5. Blocked or failed movements stop the queue with an observable outcome.
6. Status accurately reflects the navigation lifecycle.
7. Automated tests cover ordering, cancellation, blocked movement, invalid requests, and compatibility.
8. Existing quality checks pass.

## Constraints

- Reuse the existing navigation implementation.
- Avoid unnecessary abstractions or dependencies.
- Do not implement `execute_route` in this assignment.
- Do not modify the experiment export schema unless strictly necessary.
- Do not weaken existing quality or architectural constraints.

Choose the API details and internal design. Document any behavioral decisions that affect agents or existing consumers.
